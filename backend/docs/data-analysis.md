## 1. Entity-Relationship Summary

```
schedule_source
    │
    ▼
manual_schedule_entries ──────────────────────────┐
                                                   │ (expand 14 days)
                                                   ▼
preferences ──────────────────────────────► busy_events
    │                                              │
    │                                              │ (gap engine reads both)
    │                                              ▼
    └─────────────────────────────────────► nudge_plans
                                                   │
                                                   │ (user walks)
                                                   ▼
                                            walk_sessions ◄── walk_pause_events
                                                   │
                                                   ▼
                                            walk_routes

achievements     (derived from walk_sessions aggregates)
analytics_events (independent append-only event log)
```

**Key join paths:**

| From | To | Join Key | Meaning |
|---|---|---|---|
| `nudge_plans` | `walk_sessions` | `nudge_plan_id` | Was this walk nudge-driven? |
| `walk_sessions` | `walk_routes` | `session_id` | GPS trail per session |
| `walk_sessions` | `walk_pause_events` | `session_id` | Pause behaviour per session |
| All tables | user | `user_id` (backend) | Cross-table user analysis |

## 2. Data Flow

```
1. USER IMPORTS SCHEDULE
   ICS file / Google Calendar / Manual entry
          │
          ▼
   manual_schedule_entries  ← weekly recurring template

2. ON SAVE → GAP ENGINE EXPANSION
   Template expanded 14 days forward
          │
          ▼
   busy_events  ← actual time blocks on specific dates

3. GAP ENGINE RUNS
   Reads busy_events + preferences (buffer, min_walk_minutes, quiet hours)
          │
          ▼
   nudge_plans  ← walking windows identified in free gaps

4. NOTIFICATION SENT
   nudge_plans.status: 'planned' → 'notified'

5. USER WALKS (or doesn't)
   Completed  → nudge_plans.status = 'completed'
   Ignored    → nudge_plans.status = 'missed'
   Dismissed  → nudge_plans.status = 'cancelled'

6. WALK RECORDED
   walk_sessions  ← one row per walk
   walk_routes    ← GPS breadcrumbs
   walk_pause_events ← each pause

7. SYNC TO BACKEND (PostgreSQL / Supabase)
   All tables upserted via local_id + user_id composite key
```

## 3. Data Dictionary

### `busy_events`

Actual time blocks marking the user as unavailable. Derived from `manual_schedule_entries` or direct import.

| Field | Type | Notes |
|---|---|---|
| `id` | TEXT PK | Device-generated UUID. `me-gcal-*` = Google origin, `me-ics-*` = ICS origin, plain UUID = manual |
| `title` | TEXT | Event name (may be blank for privacy-scrubbed imports) |
| `start` | ISO 8601 | Local time with timezone offset |
| `end` | ISO 8601 | Local time with timezone offset |
| `source` | ENUM | `'ics'` \| `'manual'` \| `'google'` |
| `is_all_day` | BOOLEAN | If true, gap engine skips this event |
| `created_at` | ISO 8601 | Row insertion time - used for staleness detection |

---

### `manual_schedule_entries`

User's weekly recurring schedule template. Source of truth; `busy_events` is derived from this.

| Field | Type | Notes |
|---|---|---|
| `id` | TEXT PK | |
| `title` | TEXT | Block label (e.g. "Work", "School") |
| `day_of_week` | INTEGER | 0 = Sunday … 6 = Saturday |
| `start_time` | TEXT | `HH:MM` 24-hour |
| `end_time` | TEXT | `HH:MM` 24-hour |
| `is_one_time` | BOOLEAN | One-off override rather than weekly recurring |
| `one_time_date` | TEXT \| NULL | `YYYY-MM-DD` - only set when `is_one_time = true` |

---

### `nudge_plans`

Walking opportunities generated by the gap engine. One row per candidate walk window.

| Field | Type | Notes |
|---|---|---|
| `id` | TEXT PK | |
| `date` | TEXT | `YYYY-MM-DD` - calendar day this plan belongs to |
| `gap_start` | ISO 8601 | Start of the free gap the engine identified |
| `gap_end` | ISO 8601 | End of the free gap |
| `walk_start` | ISO 8601 | Suggested walk start (offset from `gap_start` by buffer) |
| `suggested_duration_minutes` | INTEGER | Engine recommendation (≥ `preferences.min_walk_minutes`) |
| `status` | ENUM | `'planned'` → `'notified'` → `'completed'` \| `'missed'` \| `'cancelled'` |
| `reason` | TEXT \| NULL | Cancellation/miss reason (e.g. `"user_dismissed"`, `"no_gps"`) |

**Status lifecycle:**
```
planned → notified → completed   ✓ success
                   ↘ missed      ✗ no walk started after notification
         → cancelled             ✗ dismissed before notification
```

> Exclude `status = 'planned'` from conversion denominators - these haven't had the opportunity to convert yet.

### `walk_sessions`

One row per completed (or recovered) walk.

| Field | Type | Notes |
|---|---|---|
| `id` | TEXT PK | |
| `nudge_plan_id` | TEXT \| NULL | FK → `nudge_plans.id`. NULL = organic walk (not nudge-driven) |
| `start` | ISO 8601 | Walk start time |
| `end` | ISO 8601 | Walk end time (including pauses) |
| `active_seconds` | INTEGER | Time actually moving (excludes pauses) |
| `paused_seconds` | INTEGER | Total time paused |
| `distance_meters` | REAL | GPS-derived distance |
| `steps` | INTEGER \| NULL | Pedometer steps (null if unavailable) |
| `calories` | REAL \| NULL | Estimated calories |
| `used_location` | BOOLEAN | Whether GPS was active |
| `pause_count` | INTEGER | Number of pause events |
| `avg_speed_mps` | REAL | `distance_meters / active_seconds` |
| `was_recovered` | BOOLEAN | App was killed mid-walk; session reconstructed on relaunch |

> Exclude `was_recovered = true` from timing analyses - `start` time may be inaccurate.

| Field | Type | Notes |

| `longitude` | REAL | WGS-84 degrees |
| `accuracy_meters` | REAL | Filter `> 20 m` for noisy points |
| `altitude_meters` | REAL \| NULL | Null on devices without barometer |
| `speed_mps` | REAL \| NULL | Instantaneous GPS speed |
| `bearing_degrees` | REAL \| NULL | 0–360° heading |
| `recorded_at` | ISO 8601 | Timestamp of the GPS fix |

## 4. North Star Metric

> **Weekly Active Walk Minutes per User**
>
> `SUM(active_seconds) / 60` per user per week, averaged across active users.

This is the single number that captures both engagement (did they walk?) and depth (how long?). All feature decisions should be evaluated against movement in this metric.

**Supporting guardrail metrics** (must not regress):
- Day-7 retention rate
- Nudge-to-walk conversion rate
- App uninstall rate (tracked externally via store analytics)

## 5. Key Derived Metrics

| Metric | Formula |
|---|---|
| **Nudge-to-walk conversion** | `COUNT(sessions with nudge_plan_id) / COUNT(nudge_plans WHERE status IN ('notified','completed','missed'))` |
| **Plan completion rate** | `COUNT(nudge_plans WHERE status='completed') / COUNT(nudge_plans WHERE status != 'planned')` |
| **Gap utilisation** | `AVG(active_seconds/60) / AVG(suggested_duration_minutes)` per completed session |
| **Organic walk rate** | `COUNT(sessions WHERE nudge_plan_id IS NULL) / COUNT(sessions)` |
| **Average active walk time** | `AVG(active_seconds) / 60` minutes |
| **Daily target attainment** | Days where `SUM(active_seconds)/60 >= daily_target_minutes` / total active days |
| **Pause frequency** | `AVG(pause_count)` per session |
| **GPS coverage rate** | `COUNT(sessions WHERE used_location=true) / COUNT(sessions)` |
| **Recovery rate** | `COUNT(sessions WHERE was_recovered=true) / COUNT(sessions)` |
| **Schedule source distribution** | `COUNT(DISTINCT user_id) GROUP BY type` on `schedule_source` |

## 6. Retention & Habit Formation

These are the most important queries for understanding whether the product creates lasting behaviour change.

### Day-1 / Day-7 / Day-30 Retention

```sql
WITH first_walk AS (
    SELECT user_id, MIN(start::date) AS day0
    FROM walk_sessions
    GROUP BY user_id
)
SELECT
    date_trunc('week', fw.day0)                              AS cohort_week,
    COUNT(DISTINCT fw.user_id)                               AS cohort_size,
    COUNT(DISTINCT CASE
        WHEN ws.start::date BETWEEN fw.day0+1  AND fw.day0+1  THEN ws.user_id END) AS d1_retained,
    COUNT(DISTINCT CASE
        WHEN ws.start::date BETWEEN fw.day0+6  AND fw.day0+8  THEN ws.user_id END) AS d7_retained,
    COUNT(DISTINCT CASE
        WHEN ws.start::date BETWEEN fw.day0+29 AND fw.day0+31 THEN ws.user_id END) AS d30_retained
FROM first_walk fw
LEFT JOIN walk_sessions ws ON ws.user_id = fw.user_id AND ws.start::date > fw.day0
GROUP BY 1
ORDER BY 1 DESC;
```

### Habit Loop Signal (48-hour re-walk rate)

Did the user walk again within 48 hours of their first walk? This is the strongest early indicator of habit formation.

```sql
WITH ordered AS (
    SELECT
        user_id,
        start::date AS walk_date,
        LAG(start::date) OVER (PARTITION BY user_id ORDER BY start) AS prev_walk_date
    FROM walk_sessions
)
SELECT
    ROUND(100.0 * SUM(CASE WHEN walk_date - prev_walk_date <= 2 THEN 1 END)
          / NULLIF(COUNT(*), 0), 1) AS within_48h_pct
FROM ordered
WHERE prev_walk_date IS NOT NULL;
```

### Streak Analysis

```sql
WITH daily AS (
    SELECT DISTINCT user_id, start::date AS walk_date
    FROM walk_sessions
),
gaps AS (
    SELECT
        user_id,
        walk_date,
        walk_date - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY walk_date)::int AS streak_group
    FROM daily
),
streaks AS (
    SELECT user_id, streak_group, COUNT(*) AS streak_length
    FROM gaps
    GROUP BY 1, 2
)
SELECT
    user_id,
    MAX(streak_length) AS longest_streak_days,
    AVG(streak_length) AS avg_streak_days
FROM streaks
GROUP BY 1
ORDER BY 2 DESC;
```

### Churn Definition & At-Risk Users

> **Churned:** No walk in the last 14 days.
> **At-risk:** Last walk 8–13 days ago.

```sql
SELECT
    user_id,
    MAX(start::date)                        AS last_walk_date,
    CURRENT_DATE - MAX(start::date)         AS days_since_last_walk,
    CASE
        WHEN CURRENT_DATE - MAX(start::date) >= 14 THEN 'churned'
        WHEN CURRENT_DATE - MAX(start::date) >= 8  THEN 'at_risk'
        ELSE 'active'
    END                                     AS status
FROM walk_sessions
GROUP BY 1
ORDER BY 2 ASC;
```

## 7. User Segmentation Framework

Segment users before analysing - behaviours differ dramatically between groups.

| Segment | Definition |
|---|---|
| **New** | First walk < 7 days ago |
| **Active** | Walk in last 7 days, first walk ≥ 7 days ago |
| **Lapsing** | Last walk 8–13 days ago |
| **Churned** | No walk in 14+ days |
| **Power user** | ≥ 5 walks in last 7 days OR weekly active minutes ≥ `daily_target * 5` |

**Schedule source as a segmentation dimension:**

Analyse all key metrics (retention, conversion, walk duration) broken down by `schedule_source.type` - ICS, Google, and manual users likely have very different behaviour profiles and churn patterns.

```sql
SELECT
    ss.type                                                  AS source,
    COUNT(DISTINCT ws.user_id)                               AS users,
    ROUND(AVG(ws.active_seconds)/60, 1)                      AS avg_active_min,
    ROUND(100.0 * SUM(CASE WHEN np.status='completed' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS plan_completion_pct
FROM walk_sessions ws
LEFT JOIN nudge_plans np ON np.id = ws.nudge_plan_id
JOIN schedule_source ss  ON ss.user_id = ws.user_id
GROUP BY 1;
```

## 8. Causal & Correlative Analyses

These answer "what should we change next?" - descriptive metrics alone cannot.

### Does `buffer_minutes` affect plan completion?

```sql
SELECT
    p.buffer_minutes,
    COUNT(np.id)                                             AS plans,
    ROUND(100.0 * SUM(CASE WHEN np.status='completed' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS completion_pct
FROM nudge_plans np
JOIN preferences p ON p.user_id = np.user_id
WHERE np.status != 'planned'
GROUP BY 1
ORDER BY 1;
```

### Does `notification_count_per_day` drive engagement or annoyance?

```sql
SELECT
    p.notification_count_per_day,
    COUNT(DISTINCT np.user_id)                               AS users,
    ROUND(100.0 * SUM(CASE WHEN np.status='completed' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS conversion_pct,
    ROUND(100.0 * SUM(CASE WHEN np.status='cancelled' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS dismissal_pct
FROM nudge_plans np
JOIN preferences p ON p.user_id = np.user_id
WHERE np.status != 'planned'
GROUP BY 1
ORDER BY 1;
```

### Does `strictness_mode` correlate with retention?

```sql
SELECT
    p.strictness_mode,
    COUNT(DISTINCT ws.user_id)                               AS users,
    ROUND(AVG(ws.active_seconds)/60, 1)                      AS avg_active_min,
    -- 7-day retention approximation
    ROUND(100.0 * COUNT(DISTINCT CASE
        WHEN ws.start::date >= CURRENT_DATE - 7 THEN ws.user_id END)
          / NULLIF(COUNT(DISTINCT ws.user_id), 0), 1)        AS recent_active_pct
FROM walk_sessions ws
JOIN preferences p ON p.user_id = ws.user_id
GROUP BY 1;
```

### Which `min_walk_minutes` setting produces most completed walks?

```sql
SELECT
    p.min_walk_minutes,
    COUNT(np.id)                                             AS plans_sent,
    ROUND(AVG(np.suggested_duration_minutes), 1)             AS avg_suggested_min,
    ROUND(100.0 * SUM(CASE WHEN np.status='completed' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS completion_pct
FROM nudge_plans np
JOIN preferences p ON p.user_id = np.user_id
WHERE np.status != 'planned'
GROUP BY 1
ORDER BY 3 DESC;
```

## 9. Suggested SQL Queries

### Weekly Active Users (WAU)

```sql
SELECT
    date_trunc('week', start) AS week,
    COUNT(DISTINCT user_id)   AS wau
FROM walk_sessions
GROUP BY 1
ORDER BY 1 DESC;
```

### Nudge Plan Completion % by Week

```sql
SELECT
    date_trunc('week', date::date) AS week,
    ROUND(100.0 * SUM(CASE WHEN status='completed' THEN 1 END)
          / NULLIF(COUNT(*), 0), 1) AS completion_pct
FROM nudge_plans
WHERE status != 'planned'
GROUP BY 1
ORDER BY 1 DESC;
```

### Nudge-to-Walk Conversion Funnel

```sql
SELECT
    COUNT(*)                                                  AS plans_notified,
    SUM(CASE WHEN status='completed' THEN 1 END)              AS completed,
    SUM(CASE WHEN status='missed'    THEN 1 END)              AS missed,
    SUM(CASE WHEN status='cancelled' THEN 1 END)              AS cancelled,
    ROUND(100.0 * SUM(CASE WHEN status='completed' THEN 1 END)
          / NULLIF(COUNT(*), 0), 1)                           AS conversion_pct
FROM nudge_plans
WHERE status IN ('completed','missed','cancelled');
```

### Average Walk Duration by Schedule Source

```sql
SELECT
    ss.type                              AS schedule_source,
    ROUND(AVG(ws.active_seconds)/60, 1) AS avg_active_minutes,
    COUNT(ws.id)                         AS sessions
FROM walk_sessions ws
JOIN schedule_source ss ON ss.user_id = ws.user_id
GROUP BY 1
ORDER BY 2 DESC;
```

### Schedule Source Distribution

```sql
SELECT
    type,
    COUNT(DISTINCT user_id)   AS users,
    ROUND(100.0 * COUNT(DISTINCT user_id)
          / SUM(COUNT(DISTINCT user_id)) OVER (), 1) AS pct
FROM schedule_source
GROUP BY 1
ORDER BY 2 DESC;
```

### Daily Target Attainment Rate

```sql
WITH daily AS (
    SELECT
        ws.user_id,
        ws.start::date                AS day,
        SUM(ws.active_seconds)/60.0   AS active_minutes,
        MAX(p.daily_target_minutes)   AS target
    FROM walk_sessions ws
    JOIN preferences p ON p.user_id = ws.user_id
    GROUP BY 1, 2
)
SELECT
    ROUND(100.0 * SUM(CASE WHEN active_minutes >= target THEN 1 END)
          / NULLIF(COUNT(*), 0), 1) AS target_attainment_pct
FROM daily;
```

### Top Pause Reasons

```sql
SELECT
    pause_reason,
    pause_source,
    COUNT(*)                                  AS occurrences,
    ROUND(AVG(pause_duration_seconds), 0)     AS avg_duration_sec
FROM walk_pause_events
WHERE pause_reason IS NOT NULL
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 20;
```

## 10. Analytics Events Taxonomy

`analytics_events` is only useful if events are logged consistently. Required events:

| Event Name | Trigger | Required Payload Fields |
|---|---|---|
| `app_opened` | App foregrounded | `session_id`, `app_version` |
| `schedule_setup_started` | User taps schedule setup | `source_type` |
| `schedule_setup_completed` | Schedule saved successfully | `source_type`, `entry_count` |
| `schedule_setup_abandoned` | User exits without saving | `source_type`, `step_reached` |
| `nudge_sent` | Notification delivered | `nudge_plan_id`, `suggested_duration_minutes` |
| `nudge_tapped` | User opens app from notification | `nudge_plan_id` |
| `nudge_dismissed` | User dismisses notification | `nudge_plan_id` |
| `walk_started` | Walk session begins | `session_id`, `nudge_plan_id` (nullable) |
| `walk_paused` | User or auto-pause | `session_id`, `pause_source` |
| `walk_resumed` | Walk unpaused | `session_id`, `pause_duration_seconds` |
| `walk_completed` | Walk session ends normally | `session_id`, `active_seconds`, `distance_meters` |
| `walk_abandoned` | User ends walk early | `session_id`, `active_seconds`, `reason` |
| `preferences_changed` | Any setting modified | `field_name`, `old_value`, `new_value` |
| `achievement_unlocked` | Achievement granted | `achievement_id` |

> Add `app_version` and `platform` (`'android'`) to every event payload.

## 11. Experiment Design

### Schema Addition Required

Before running any A/B test, add an experiment assignment table to the backend:

```sql
CREATE TABLE experiment_assignments (
    user_id     UUID        NOT NULL,
    experiment  TEXT        NOT NULL,   -- e.g. 'buffer_minutes_test_2026q2'
    variant     TEXT        NOT NULL,   -- e.g. 'control' | 'treatment_5min' | 'treatment_10min'
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, experiment)
);
```

### Minimum Sample Size

For a conversion rate experiment (current baseline ~X%):

| Baseline | Minimum Detectable Effect | Users per Variant |
|---|---|---|
| 30% | 5 pp (to 35%) | ~800 |
| 30% | 3 pp (to 33%) | ~2,200 |
| 50% | 5 pp (to 55%) | ~750 |

Use a power calculator with α = 0.05, power = 0.80.

### Avoiding Novelty Effects

- Run experiments for a minimum of **2 full weeks** to smooth weekly usage patterns.
- Use the user's first assignment date, not the experiment start date, for cohort analysis.
- Exclude users assigned in the last 3 days from final analysis (incomplete exposure).

### Analysis Template

```sql
SELECT
    ea.variant,
    COUNT(DISTINCT ws.user_id)                               AS users,
    ROUND(AVG(ws.active_seconds)/60, 1)                      AS avg_active_min,  -- North Star
    ROUND(100.0 * SUM(CASE WHEN np.status='completed' THEN 1 END)
          / NULLIF(COUNT(np.id), 0), 1)                      AS plan_completion_pct
FROM experiment_assignments ea
LEFT JOIN walk_sessions ws  ON ws.user_id = ea.user_id
LEFT JOIN nudge_plans np    ON np.user_id = ea.user_id AND np.status != 'planned'
WHERE ea.experiment = '<experiment_name>'
GROUP BY 1;
```

## 12. Data Quality Notes

### Stale `busy_events`

- The gap engine expands the weekly template **14 days forward** on each schedule save.
- Events older than 14 days are not refreshed automatically.
- Filter `start >= CURRENT_DATE` for operational analysis.
- After a schedule source change, old events from the previous source may persist until the next expansion. Use the `source` field to detect mixed-source contamination.

### `id` / `local_id` Naming Conventions

| Prefix | Origin |
|---|---|
| `me-gcal-*` | Google Calendar import |
| `me-ics-*` | ICS file import |
| Plain UUID | Manual entry or system-generated |

The backend uses `local_id` + `user_id` as a composite dedup key on upsert. Watch for duplicate rows if a device syncs the same event before and after a schema migration.

### `walk_sessions.was_recovered`

Sessions with `was_recovered = true` have reconstructed `start` times. Exclude from latency and timing analyses.

### `walk_routes` Volume

~720 rows per 1-hour session. Always aggregate or filter before joining at scale. Apply `accuracy_meters < 20` as a baseline quality filter for distance calculations.

### `walk_pause_events` with NULL `pause_ended_at`

Indicates an in-progress or app-killed pause. Coalesce with the parent session's `end` time when computing `pause_duration_seconds`.

### `nudge_plans` with `status = 'planned'`

Future plans not yet acted on. **Always exclude from conversion and completion rate denominators.**

### `analytics_events` Schema Drift

`payload_json` is unstructured and evolves with app versions. Always filter or parse with awareness of app version. Recommend adding `app_version` to every payload if not already present.

### Clock Skew

All timestamps are client-side. Device clocks can be wrong. For backend-critical analyses (cohort assignment, retention), prefer `created_at` from the server over client-side `start`/`recorded_at` fields.
